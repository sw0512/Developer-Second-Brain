## 1. 프로젝트 축을 폴더가 아닌 메타데이터로 추가

- **상태**: 완료 (2026-07-30) — 아래 작업 항목 4건 모두 반영. 근거는 기록용으로 남긴다.
- **결정일**: 2026-07-26
- **관련 버전**: v0.3 (Notion 연동 시 property로 매핑되므로 그 전에 필드가 존재해야 함)

### 결정

문서를 프로젝트별로 나누되, **디렉터리 계층이 아니라 frontmatter 필드 `project`로** 표현한다.
vault 디렉터리 구조는 지금의 "타입 = 폴더, 예외 없음" 1단 규칙을 그대로 유지한다.

### 근거

1. **vault의 존재 이유와 충돌.** `references/vault-layout.md`는 vault가 단일 프로젝트 바깥에
   살아서 모든 repo의 지식이 한 곳에 쌓이는 것을 전제로 한다. 프로젝트별 디렉터리는 그 통합을
   되돌려서, A 프로젝트에서 얻은 교훈이 B 프로젝트 작업 중에 보이지 않게 만든다.
2. **축이 둘인데 폴더는 하나만 고를 수 있다.** `project/type`이든 `type/project`든 반대 방향
   조회가 불편해진다. 현재의 "타입 이름 = 폴더 이름" 불변식(룩업 테이블 불필요)도 깨진다.
3. **v0.3에서 폴더는 어차피 사라진다.** Notion에서 프로젝트는 중첩 DB가 아니라 property다.
   폴더로 만들면 동기화 시점에 평탄화가 필요하고, 이는 원칙 7(백엔드 교체는 한 곳만 바뀐다)
   위반이다.
4. **원칙 8이 이미 답을 정해뒀다.** "Metadata is the contract between capabilities." v1.0의
   Knowledge Graph·Weekly Report는 프로젝트 축으로 질의해야 하는데, 경로가 아니라 필드로 푸는
   것이 맞다. 프로젝트 rename·모노레포 분리 시에도 필드는 한 줄 수정, 경로는 전체 이동이다.

### 작업 항목

- [x] 템플릿 6종 frontmatter에 `project` 추가
      (`troubleshooting`, `adr`, `til`, `retrospective`, `resume-material`, `study-note`)
- [x] `references/vault-layout.md`에 "프로젝트는 폴더가 아니라 메타데이터" 근거 한 단락 추가
      — 이 규칙의 단일 authoritative 위치 (원칙 5, one concept one home)
- [x] 프로젝트 이름 추출 규칙 명시: `git remote` origin의 repo 이름 → 없으면 작업 디렉터리명
      → 둘 다 애매하면 `unknown`
- [x] `docs/architecture.md`의 vault 설명이 frontmatter 스키마를 언급한다면 동기화
      (원칙 5, documentation mirrors architecture)

### 정하지 않은 것

- 물리적으로 vault를 완전히 분리하고 싶은 경우(회사/개인 repo 분리 등)는 이미 있는
  `SECOND_BRAIN_VAULT` 환경변수로 vault 루트를 갈아끼우면 된다. 별도 기능을 만들지 않는다.

## 2. 채팅(claude.ai)에서의 사용 — 독립 기능이 아니라 v0.3에 종속

- **상태**: 미착수 — v0.3 착수 시 함께 설계한다.
- **결정일**: 2026-08-02
- **관련 버전**: v0.3 (Notion 연동). 그 전에는 착수하지 않는다.

### 계기

Claude Code에서는 "공부"가 잘 일어나지 않는다. 볼트 13개의 실제 분포가 이를 보여준다 —
`troubleshooting` 6, `how-to` 4, `til` 3, 그리고 **`adr`·`study-note`·`retrospective`·
`resume-material`은 0개**다. 7종 중 4종이 한 번도 쓰이지 않았다. 학습·회고성 작업이 주로
채팅에서 일어난다면, 캡처가 Code에만 있는 한 그 지식은 계속 증발한다. 이는 원칙 2의
"경험이 증발한다"를 그대로 재현하는 것이므로 무시할 문제가 아니다.

### 결정

채팅 지원을 **독립 기능으로 만들지 않는다.** v0.3(Notion 저장소)의 파생 효과로 얻는다.

### 근거

1. **막히는 것은 스킬이 아니라 저장소다.** 판단·유형 선택·초안까지는 채팅에서 그대로 돈다.
   `~/DeveloperSecondBrain/`이 로컬 경로라서 **쓰는 순간에만** 죽는다. 채팅의 실행 환경은
   사용자 로컬 디스크에 닿지 않고 세션과 함께 사라진다.
2. **원칙 7이 이미 답이다.** 저장소는 추상적이고 교체 가능해야 한다. Notion은 네트워크
   백엔드라 채팅에서도 커넥터로 닿는다. v0.3이 끝나면 채팅 지원은 자동으로 따라온다.
3. **순서를 뒤집으면 백엔드가 둘이 된다.** v0.3 전에 채팅용 저장을 따로 만들면 "백엔드 교체는
   한 곳만 바뀐다"가 깨진다. 원칙 7 정면 위반이고, 나중에 합칠 때 마이그레이션 비용을 새로 만든다.
4. **스킬 이식 비용은 이미 지불돼 있다.** 원칙 5의 "A capability owns its assets" 덕분에
   `skills/second-brain/`이 references·templates까지 자립해 있어, 디렉터리 하나만 떼면 된다.
   리포 전체는 Claude Code 플러그인(`.claude-plugin/`, hooks, commands)이라 통째로는 못 옮긴다.
5. **훅이 빠지는 것은 손해가 아니다.** 채팅에는 훅이 없으므로 자동 탐지는 Code 전용으로 남고,
   채팅에서는 `/document` 같은 수동 진입만 가능하다. Commands(수동)와 Hooks(자동)를 별도 레이어로
   나눠 둔 이유가 정확히 이것 — 훅 레이어가 없어도 나머지가 그대로 동작한다.

### 작업 항목 (v0.3 착수 시)

- [ ] v0.3 저장소 경계를 설계할 때 "로컬 파일 아님"을 전제로 둘 것 — 채팅 실행 환경에서도
      같은 경로로 쓸 수 있어야 한다.
- [ ] `skills/second-brain/`만 떼어 claude.ai 커스텀 스킬로 올릴 때 무엇이 깨지는지 확인
      (코드 실행 필요 여부, 업로드 형식, `references/` 로드 방식).
- [ ] `references/vault-layout.md`의 "vault 루트 결정" 절이 로컬 경로를 전제하고 있으므로,
      백엔드가 둘(로컬/Notion)이 되는 시점에 이 문서가 단일 authoritative 위치로 남도록 갱신.

### 정하지 않은 것

- **쓰이지 않는 4개 타입을 정리할지.** `study-note`가 0인 것은 표면(Code에서 공부를 안 함)
  탓이 크지만, `retrospective`·`resume-material`이 0인 것은 표면과 무관할 수 있다 — 회고나
  이력서 소재는 채팅에서도 "작업 중"에는 나오지 않는다. 표본이 13개뿐이라 지금 자르는 것은
  이르다. 채팅 지원 이후 분포를 다시 보고 판단한다.
